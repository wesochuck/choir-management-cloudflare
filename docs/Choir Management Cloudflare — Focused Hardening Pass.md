## Priority 1 — Restore CSP for Static Assets & Prevent Drift

### Problem

The Worker configuration now correctly uses selective Worker-first routing:

```json
"run_worker_first": ["/api/*"]
```

This means normal SPA assets and HTML are served directly by Cloudflare Static Assets.

The Worker applies a Content Security Policy through `setSecurityHeaders()` in
`apps/worker/src/router.ts`, but static assets served directly do not pass through that Worker code.

`apps/web/public/_headers` currently contains only:

- `X-Frame-Options`
- `X-Content-Type-Options`
- `Referrer-Policy`

As a result, the application's static HTML does not receive an equivalent CSP when served directly
via Static Assets.

### Required change

1. Add an appropriate `Content-Security-Policy` header to: `apps/web/public/_headers`

2. Base it on the policy generated by `buildContentSecurityPolicy()` in `apps/worker/src/router.ts`.
   Specifically enforce:
   - `default-src 'self'`
   - `base-uri 'self'`
   - `object-src 'none'`
   - `frame-ancestors 'none'`
   - `form-action 'self'`
   - `script-src 'self' https://static.cloudflareinsights.com https://challenges.cloudflare.com` (do
     not attempt dynamic nonces in static `_headers`)
   - `style-src 'self' 'unsafe-inline'`
   - `img-src 'self' data: blob:`
   - `font-src 'self' data:`
   - `connect-src 'self' https://cloudflareinsights.com https://challenges.cloudflare.com`
   - `frame-src 'self' https://challenges.cloudflare.com`
   - `media-src 'self' blob:`
   - `worker-src 'self' blob:`
   - `manifest-src 'self'`

### Prevent CSP drift

1. Create a lightweight check script (e.g. `scripts/check-csp.mjs`) or share directive definitions
   between `router.ts` and `_headers` validation.
2. Wire the check script into `scripts/check-ci.mjs` under the `static` job group and add a
   corresponding `npm run check:csp` script in `package.json`.
3. Automated coverage must verify:
   - `_headers` includes `Content-Security-Policy`.
   - All required directives are present and syntactically valid.
   - The static policy remains semantically aligned with the Worker's static policy baseline
     (excluding per-request nonces).
   - Cloudflare Insights (`https://static.cloudflareinsights.com`, `https://cloudflareinsights.com`)
     and Cloudflare Turnstile/Challenge (`https://challenges.cloudflare.com`) origins are properly
     allowed.
   - `frame-ancestors 'none'` and `object-src 'none'` remain strictly enforced.

## Priority 2 — Finish the RSVP TanStack Query Migration

Relevant files:

- `apps/web/src/account/hooks/useRsvpQueries.ts`
- `apps/web/src/account/RsvpManagerPage.tsx`
- `apps/web/src/api/queryKeys.ts`
- `apps/web/src/api/events.ts`

### 2A — Surface RSVP history errors independently

Currently, attendance query errors are surfaced in the UI, but RSVP history loading errors are
swallowed or coupled with attendance loading state.

Desired behavior:

- Roster view and attendance operations must continue functioning if only RSVP history fails to
  fetch.
- If attendance loading fails, display the blocking error notice for the roster as usual.
- If history loading fails while attendance succeeds:
  - Keep the roster view fully operational.
  - When the user switches to the **Event RSVP History** tab (`view === "history"`), display a
    prominent, accessible error notice (e.g. `role="alert"` / `notice notice--error`) stating that
    RSVP history could not be loaded, with an option to retry.
- History loading state (`historyQueryData.isLoading`) must not block or show a full-page loading
  spinner when viewing the Roster tab.

### 2B — Authoritative query cache updates on mutations

Avoid UI lag where a mutation completes, a success message ("RSVP updated") is displayed, but the
table continues showing stale data until background refetch finishes.

1. **Single RSVP update (`useSetRsvpMutation`)**:
   - `setOrganizationEventRsvp` returns `OrganizationRsvp`
     (`{ profileId, rsvp, rsvpNote, eventId, updatedAt }`).
   - In `onSuccess`, update the `queryKeys.organization.attendance(eventId)` query cache immediately
     using `queryClient.setQueryData`:
     - Update the matching profile's `rsvp` and `updatedAt`.
   - Invalidate `queryKeys.organization.attendance(eventId)` and
     `queryKeys.organization.rsvpHistory(eventId)` in the background for eventual reconciliation.

2. **Bulk RSVP update (`useBulkUpdateRsvpMutation`)**:
   - `bulkUpdateOrganizationEventRsvp` returns `readonly OrganizationAttendanceRow[]` (the updated
     attendance rows).
   - In `onSuccess`, update the `queryKeys.organization.attendance(eventId)` query cache immediately
     with the returned updated rows.
   - Invalidate `queryKeys.organization.attendance(eventId)` and
     `queryKeys.organization.rsvpHistory(eventId)` in the background.

### 2C — Integrate with canonical `queryKeys.ts`

Instead of creating an isolated query-key factory, extend the existing centralized
`apps/web/src/api/queryKeys.ts`:

```ts
export const queryKeys = {
  // ...
  organization: {
    // ...
    attendance: (eventId: string) => ["organization", "events", eventId, "attendance"] as const,
    rsvpBootstrap: ["organization", "rsvp", "bootstrap"] as const,
    rsvpHistory: (eventId: string) => ["organization", "events", eventId, "history"] as const,
    // ...
  },
};
```

Update `useRsvpQueries.ts` to import and use `queryKeys.organization.*`.

### Tests

Add and update automated tests covering:

- Single RSVP mutation updating attendance cache immediately.
- Bulk RSVP mutation updating attendance cache immediately.
- Background invalidation firing for attendance and history queries on mutation success.
- Independent handling of history query failure vs attendance query failure.
- RsvpManagerPage displaying history error message only when history fails and history tab is
  active.
- Event switching resetting selection and loading appropriate event cache.

## Priority 4 — Pragmatic Frontend API Barrel Cleanup

### Assessment

`apps/web/src/auth/api.ts` is currently a 2-line compatibility re-export
(`export * from "../api";`).

Over 50 components across `apps/web/src/account/` currently import from `../auth/api` or
`../../auth/api`.

### Guidance

- **Do not perform a mass 50-file search-and-replace churn** across untouched files purely to
  eliminate the 2-line re-export. Mass import churn creates high merge friction and noise in git
  history without functional benefit.
- **Update imports to `apps/web/src/api` in all files touched during this hardening pass** (e.g.
  `useRsvpQueries.ts`, `RsvpManagerPage.tsx`, etc.).
- Retain `apps/web/src/auth/api.ts` with a `@deprecated` annotation pointing developers to
  `apps/web/src/api` until remaining pages are migrated naturally during feature maintenance.
